# Architecture

The components of Kronoer, where data lives, and how it is encrypted. This file is the source of truth for the architecture; change it in the same pull request as the code it describes.

## Components

| Component      | Technology                         | Role                                             | Phase |
| -------------- | ---------------------------------- | ------------------------------------------------ | ----- |
| App            | Flutter (Android first)            | UI, local storage, i18n                          | MVP   |
| Core           | Rust via flutter_rust_bridge       | All cryptography and the entry/Book format       | MVP   |
| Server         | Go (Connect-RPC, pgx, sqlc, goose) | Auth, sync, shared Books, key distribution, push | V1    |
| Database       | PostgreSQL                         | Metadata, wrapped keys, encrypted entries        | V1    |
| Object storage | S3-compatible                      | Encrypted images, uploaded via presigned URLs    | V1    |

The server never holds a key that can open content.

## Repository

Public monorepo. Folders: `app/`, `core/`, `spec/`, `server/`, `proto/`.

Licenses: `core/` and `spec/` are `MIT OR Apache-2.0`; `app/`, `proto/`, and `server/` are `AGPL-3.0-only`.

## Storage

| Data                    | Where                                                                          | Login |
| ----------------------- | ------------------------------------------------------------------------------ | ----- |
| Personal Book (default) | Device: SQLCipher database of per-entry encrypted blobs, encrypted image files | No    |
| Personal Book with sync | Device + server, same encrypted blobs                                          | Yes   |
| Shared Book             | Server is the source of truth; devices keep a cache                            | Yes   |

- Local and server use **the same per-entry encrypted format**, so sync uploads blobs as they are.
- No Google Drive backup. Users without sync are protected by export & import.
- Export is an unencrypted Archive (every Book not in the Trash, Locked Books included, with its Entries and Images, stars, and locks) with a clear warning. Its format is `spec/export-format.md`. Import adds only what a device lacks, sealed with that device's keys; it never overwrites.

### On the device

The core owns local storage (`kronoer_core::store`); the app reaches it through `kronoer_bridge` and sends and receives only plaintext content and IDs.

- **One SQLCipher database** (`rusqlite` with bundled SQLCipher and vendored OpenSSL), opened with the `kronoer/v1/sqlcipher` subkey as a raw key and SQLCipher 4's cipher settings pinned, in WAL mode. The schema version is `PRAGMA user_version`; the core runs migrations when it opens the database and refuses a newer one. A migration is SQL from `core/src/store/migrations/` (built into the core), optionally followed by a step that needs the Book keys, in one transaction. Before the first release the schema was folded into version 1; from then on a migration that has shipped never changes.
- **Tables:** `book` (name, Description, Cover's Image ID, last activity, sealed Book record), `book_key` (wrapped Book keys by version), `entry` (header fields, created and updated times, sealed blob), `entry_image` (Images of each Entry, in order), `entry_search` (FTS5, `unicode61 remove_diacritics 2`, keeps the text for snippets and list previews), `book_pin` (the Pinned Books), `book_out_of_timeline` (the Books kept out of the Timeline), `star` (Star records, with the Entry ID, Book ID, and starring time beside each), `book_lock` (Lock records, with the Book ID and locking time beside each), `book_trash` and `entry_trash` (the Books and Entries in the Trash, with when each was deleted), and `trash_setting` (how many days the Trash keeps them).
- **The blobs are the data.** Every plaintext column and the search index are written in the same transaction as the blob, and `rebuild_index` rebuilds them from the blobs. `book_pin` and `book_out_of_timeline` are the exceptions: a pin, like keeping a Book out of the Timeline, is this device's own choice, so it is kept only there, outside the sealed Book record, and is not exported or sent. A Book is in the Timeline unless it is listed in `book_out_of_timeline` (`set_book_in_timeline`). Deleting a Book removes both (`ON DELETE CASCADE`). A star is the user's own too, but follows them to other devices, so it is a sealed record of its own rather than a column: `set_entries_starred` stars or unstars several Entries in one transaction without touching their blobs, `updated_at`, or their Book's activity; `list_starred_entries` pages a Book's Starred Entries, newest first; moving an Entry seals its Star record again with the new Book ID; deleting the Entry for good deletes it (`ON DELETE CASCADE`), while the Entry in the Trash keeps it. Every Entry a list returns says whether it is starred. A Book lock is the user's own and follows them the same way, as a sealed Lock record in `book_lock`: `set_books_locked` locks or unlocks several Books in one transaction, unpins each Book it locks and keeps its Timeline choice; `list_books` leaves Locked Books out and `list_locked_books` lists only them; the Timeline (`list_all_entries`, `oldest_timeline_day`, `timeline_days`) leaves them out whatever their Timeline choice, and `search` across all Books leaves them out of its hits and per-Book counts, while a search within one Book, locked or not, works as usual; each Trash item from a Locked Book says so (`BookInfo::locked`, `book_locked` on an Entry); a Book in the Trash keeps its lock, so restoring brings it back locked, and deleting the Book for good deletes it (`ON DELETE CASCADE`). A lock is not encryption: the Book's record, key, and Entries stay as they are. At most 3 Books are pinned (`MAX_PINNED_BOOKS`): `set_books_pinned` pins or unpins several in one transaction and changes nothing if that would pass the limit.
- **Images** are files named `<Image ID>.full` and `<Image ID>.thumb`, each one sealed Image blob. A save writes new files atomically (temporary file, sync, rename) before its transaction and deletes them if the transaction fails. A delete removes rows first and files after. A Book's Cover is stored the same way, under its own Image ID, and replacing or removing it, or deleting the Book for good, deletes its files after the commit. At open, files no Entry or Book Cover refers to and older than one hour are removed.
- **Trash:** deleting moves a Book or Entries to the Trash rather than deleting them: `trash_book` and `trash_entries` add a row to `book_trash` or `entry_trash` with the deletion time, and touch no blob. Like a pin, the Trash is this device's own state, outside the sealed records, so it is not exported or sent. A Book goes with its Entries: they get no row of their own, unless one was deleted before the Book, and then it stays an item of its own. Trashing a Book also drops its pin and its Timeline choice, so restoring does not bring them back; Images, Cover, and stars stay. Every listing leaves out what is in the Trash: a Book's Entries and counts, its last activity, and its insight skip the Entries trashed on their own; the Book list skips trashed Books; the Timeline, its date strip, and search skip both. `get_book`, `get_entry`, and the Images still open what is in the Trash, for its read-only view. `restore` takes Books and Entries out in one transaction; an Entry whose Book is still in the Trash goes to another Book (`others_to`, moved and sealed again as a move does) or brings its Book back too. `list_trash` lists both kinds, the one deleted most recently first, each with when it is deleted for good. `delete_forever` and `empty_trash` delete rows, then files; a Book goes with all its Entries, those trashed on their own included, since they cannot outlive its Book key. Each item stays the chosen number of days from its own deletion: 7, 30, or 90 (`TRASH_DAY_CHOICES`), 30 until the user chooses (`DEFAULT_TRASH_DAYS`), kept in `trash_setting` on this device. At open, before the orphan files are removed, the core deletes for good everything deleted longer ago than that, and `set_trash_days` does the same at once when the time gets shorter. A new time with nothing to delete sends no `Change`, since no Book or Entry changed, so the app's repository re-reads its lists itself after setting it.
- **Order and search:** `list_books` lists the Pinned Books first, then the rest, each by last activity, newest first; each Book comes with its latest Entry's text and Image count and its Entry count. Entries are listed by Entry date as written (local time), newest or oldest first (`EntryOrder`), within one Book (`list_entries`) or across all of them for the Timeline (`list_all_entries`). The Timeline leaves out the Books kept out of it with a correlated `NOT EXISTS` on `book_out_of_timeline`, which keeps the walk on `entry_by_date` (a `NOT IN` subquery made SQLite sort in a temporary B-tree); the Book list, a Book's own Entries, and search ignore that choice. Entries with the same Entry date come in the order they were written (`created_at`), then by ID, and lists are paged by a cursor of those three after the last Entry of a page. One index per listing (`entry_by_book_and_date`, `entry_by_date`) serves both orders, read backwards for newest first. For the Timeline's date strip, `oldest_timeline_day` and `timeline_days` give the earliest day with an Entry and the days with Entries in a range, as `YYYY-MM-DD` at a UTC offset the app passes (the device's now), from the plaintext `entry_date` alone; SQLite's `date()` moves each Entry date to that offset. One offset serves every date, so where the clocks change for summer time, an Entry within an hour of midnight in the other half of the year can have its dot on the day next to the one the list shows it under. Since an Entry's day as written is at most two days from its day at any offset, both narrow the Entries to read with a range on `entry_by_date`. Search results always come newest first. Search matches every typed word as a word prefix, with or without diacritics, and returns snippets and the match count per Book. `match_ranges` finds the matching words in one text with the index's own tokenizer, in a throwaway in-memory database, so the read view marks exactly what the search matched. `book_insight` counts a Book's Entries and the Images of its Entries (not its Cover) from `entry` and `entry_image`, and its words from the text kept in `entry_search`, so no blob is opened. A word is a piece between white space with a letter or a digit (`count_words`), so Text style marks are not words; the app counts with the same function.
- **Moving Entries:** the Book ID is bound to an Entry blob as associated data, so `move_entries` opens each Entry with its Book's key and seals it again for the other Book's current key, with a fresh Entry key and the same Entry ID; one move is one transaction, all or nothing. Moving is not editing: the Entry date, created and updated times, text, and Images stay. Image files are not touched, since an Image blob is bound only to its Image ID and its keys travel inside the Entry. The Book moved from takes its last activity from the Entries it still has; the one moved to keeps its own unless a moved Entry is later. Undo is a move back.
- **Export** (`store/export.rs`): `export_archive` writes the Archive to any `Write` as a ZIP stream (`ZipWriter::new_stream`), so the file the user picked never has to seek, as a provider's pipe cannot. It reads what goes in (Book records, locks, stars, the Entry IDs, the Image count) under one lock first, then opens one Entry at a time, each under its own lock, so the app keeps working meanwhile: `README.txt`, then `kronoer.json` streamed Entry by Entry, then every Cover and Entry Image as its full JPEG, stored without compression. Memory stays bounded by one Entry or one Image. Progress (Entries and Images done of the total) is reported after each, and the callback's answer cancels (`StoreError::Cancelled`); a failed write is `StoreError::ArchiveWrite`, storage full included. An Image whose file is missing fails the Export rather than leaving it out. What it wrote is then not a whole Archive, and the caller deletes it.
- **Import** (`store/import.rs`): `import_archive` reads an Archive from any `Read + Seek` (`ZipArchive`, which reads the central directory at the end). It checks the whole Archive first, without the store's lock: `format` and `format_version` on their own (`StoreError::ArchiveNewer` for a newer one), then every key, ID, Entry date, time, and reference, and that every Image named has its file (`StoreError::ArchiveDamaged`, also for a ZIP cut short or a checksum that does not match; `ArchiveRead` when the file cannot be read). Under one short lock it then looks up what the store has: a Book or Entry whose ID it has is skipped wherever it is, the Trash included, whatever its `updated_at`; the new Entries of a Book in the Trash are skipped and counted; everything else is added, so a Book or Entry deleted for good comes back. With the store free again, each Image to add is prepared: its JPEG segments are walked, the metadata segments dropped without decoding the picture again (APP1, APP2 but the ICC profile, APP3 to APP13, APP15, COM, and bytes after EOI), its frame checked to be at most 2048 px a side, and it is decoded (the `image` crate, JPEG only, with that limit) to make a thumbnail of at most 512 px, quality 80 (`StoreError::ArchiveImage` for one that fails). Its two blobs are sealed with a new Image ID and key and written before anything commits; an Import that fails, is cancelled, or adds less than it prepared deletes the files it did not use. Then, in one transaction, it looks again and adds what is still missing: new Books with a new Book key, their record (Description and Cover) sealed with it, a new Lock record for those the Archive lists as locked; new Entries keeping their IDs, Entry dates, and `created_at`/`updated_at`, sealed with their Book's current key, indexed, with a new Star record for those the Archive stars. Nothing the store had changes: not its locks, stars, records, or Trash. Progress is reported once before the check and after each new Entry is ready, and the callback's answer cancels. It returns, for each Book of the Archive, its name on the device, whether it was added, locked, or in the Trash, and how many Entries were added, already there, or skipped for the Trash.
- **Keys:** a `Keyring` holds the master key and the Book keys unwrapped so far; Dart holds it only as an opaque handle. Every commit fires a change event that the app can watch.
- **Master key on Android:** the master key file `no_backup/master-key` (CBOR `[version, wrapped key]`, written atomically) holds the master key wrapped with AES-256-GCM by a non-exportable Android Keystore key (`kronoer-master-key-wrap-v1`, no user authentication or unlock condition). The core calls Keystore through JNI behind the `MasterKeyStore` trait; Kotlin's `KronoerApplication` hands it the JVM and the app's directories at process start. The database and Images live in `files/store/`. At open, the core tells apart "no master key file" from "cannot unwrap it": it makes a new master key only when neither the key file nor the database exists, and never writes or deletes anything when opening fails.
- **No Android backup:** `allowBackup` is off and the data extraction rules exclude everything from cloud backup and device transfer; the wrapped master key could not be unwrapped on another device anyway.

## App

- Two Android product flavors (KRO-ADR-17): `stable` is `app.kronoer`, and `preview` is Kronoer Preview, `app.kronoer.preview`, a separate app beside it. `default-flavor` in `pubspec.yaml` makes builds without `--flavor` the stable app. Preview has its own launcher icon (`android/app/src/preview/res/`, with `app_icon_preview` for About); Dart reads `appFlavor` through `isPreviewProvider`, which adds the mini "Preview" label to the wordmark and the Preview's name and version to About. `--split-per-abi` builds one APK per ABI, without the `abiFilters` that are set otherwise.
- Feature folders under `app/lib/src/`: `home/`, `books/`, `entries/`, `timeline/`, `search/`, `settings/`, `lock/`, `reminder/`, `trash/`, `export/`, `import/`, `welcome/`, shared `ui/` and `theme/`, and `storage/`.
- Navigation: go_router. Every screen has a path, so deep links build the same back stack. The exceptions are pushed without a path on the root navigator: the Cover crop screen, because it holds a photo not saved yet that a link could not bring back, "Pindahkan ke", which picks the Book to move Entries to and returns it to the screen that asked, and "Pulihkan ke", which does the same for Entries restored from the Trash whose Book is in the Trash too. A `StatefulShellRoute` holds three tabs behind a bottom navigation (`home/home_shell.dart`): the Book list (`/`), the Timeline (`/timeline`), and Settings (`/settings`). Each tab has its own navigator, so it keeps its screen and scroll position; every other screen is on the root navigator, over the bar. The app always opens on the Book tab, and back from another tab goes to it. The Timeline pushes the screens it opens (an Entry, search, "Book di Linimasa" at `/timeline/books`), so back returns to it. The read view likewise pushes the editor and the Image viewer, which close back to it, and deleting an Entry closes its screens back to whichever screen opened it. The Book screen's name and ⓘ open Book info (`/books/:id/info`), which holds the Book's menu: Edit name (`info/rename`) and Edit description (`info/description`) save back to Book info. Below the Description, Book info has two rows: a switch for whether the Timeline shows the Book, and Delete Book, which goes to the Book list. Settings has the Trash under data: `settings/trash` is its hub, with how long the Trash keeps items (Simpan selama), `trash/items` the list of everything in it, and `trash/items/:id` one item, read-only, with only Pulihkan and Hapus permanen (`trash/`). The Cover on Book info pushes it full screen (`info/cover`); removing the Cover there closes back to Book info.
- State: Riverpod without code generation.
- Screens reach data only through the `BookRepository`, `EntryRepository`, and `SearchRepository` providers. `CoreRepository` implements all three over the core's store (`CoreStore` in the bridge), which `main.dart` opens before the first frame; every watch reads again after each change event. If the store does not open, the app shows only an error screen and creates nothing. `InMemoryStore` remains for tests and has no search. The debug sample data (`KRONOER_SAMPLE=true`) is seeded into a core store in a new temporary folder with a master key that is never kept; `KRONOER_SAMPLE=empty` opens such a store with no Books, at Welcome, as on a new phone, and `KRONOER_CLOCK_DAYS` runs the sample app's clock that many days ahead. IDs are opaque strings of 32 hexadecimal digits, created by the core (`newId()`).
- A Book and the Timeline list their Entries newest first until another order is chosen in their ⋮ menu. The choice is not stored: it lives in an auto-disposed provider (`bookEntryOrderProvider`, `timelineOrderProvider`) that the screen keeps alive, so a Book goes back to newest first once its screen closes, and the Timeline once the app does. Which Books the Timeline shows is stored instead (in the core, see above) and changed from Book info or "Book di Linimasa" (`timeline/timeline_books_screen.dart`) through `BookRepository.setBookInTimeline`; the Timeline re-reads on the change event, so it updates at once. With Entries but every Book kept out, it says so where it would say there is no Entry yet, and its ⋮ keeps "Book di Linimasa" as the way back.
- The Book screen lists its Entries as cards under month separators (`entries/entry_list.dart`). The Timeline (`timeline/`) is a time line instead: `timelineRows` turns the Entries into rows, a heading per day with the day's Entries under it, from the later of today and the newest Entry back to the earlier of the oldest Entry and the 1st of this month. Every day shows; a run of 7 or more days with no Entry is one row, and today always has its own. Days are the device's local days, like the times shown. Oldest first turns the days around. The rows are one `SliverList`; the date strip above it (`date_strip.dart`, days of a month, months of a year, or years, under date crumbs) follows the topmost row after each scroll, read from the sliver's laid-out children once the frame is laid out. Picking a day, month, or year moves the list to its row: rows have no fixed height, so a row not laid out yet is reached by jumping to where it should be, by the average height of the rows laid out, until it is, then to it exactly. The strip's dots come from `EntryRepository.watchTimelineDays`, not from the loaded Entries. Tapping the open Timeline tab goes back to today at the day level (`ScrollToTopOnReselect.onReselect`).
- Selection mode on the Book list (`books/book_list_screen.dart`, shared pieces in `ui/selection.dart`): a long press selects a Book and a tap then selects or deselects; the selection is screen state, ended by back or by deselecting the last Book. Back reaches it through the shell (`HandleBackOnTab`), not a `PopScope` of its own: the shell's `PopScope` is what tells Android whether the app handles back, and while it says no, Android closes the app without asking. While it lasts, one animation fades the top bar to its selection look and folds away the search field and the FAB. Pinning goes through `BookRepository.setBooksPinned`, which throws `TooManyPinnedBooks` past the limit; deleting several Books moves them to the Trash one by one after one confirmation, then offers "Urungkan", which restores them and puts back their pins and Timeline choices. The same `Selection` drives selection mode on the Book screen (`books/book_screen.dart`): there a long press on an Entry card selects it, and the top bar offers Salin, Pindahkan, and Hapus while the FAB fades. The Book screen is over the tabs, so a plain `PopScope` ends it on back. Pindahkan moves at once to the Book picked (`entries/entry_moving.dart`) and shows "Urungkan"; the read view's ⋮ menu moves one Entry the same way and then closes back to whichever screen opened it. Deleting Entries, one or several, asks nothing: it moves them to the Trash and offers "Urungkan" (`trash/trash_actions.dart`).
- Copying Entries' text (`entries/entry_copying.dart`) happens in the app only, from text already open: Salin in selection mode and the read view's "Salin teks" turn each Entry's text into plain text with the Text style parser (`plainText`) under a line of its Entry date and time. The clip is marked sensitive (`ClipDescription.EXTRA_IS_SENSITIVE`), which Flutter's `Clipboard` cannot do, so on Android it goes through the `app.kronoer/clipboard` method channel in Kotlin's `MainActivity`. Android 13 and higher show their own clipboard preview, so only older versions get a snackbar. Text too large for one binder transaction (about 1 MB) is refused before it is sent, and the channel reports a clip the system still turns down; either way nothing is copied.
- Search screens (all Books, one Book) take their query from the path, search once typing pauses, and ignore an answer that arrives after a newer one was asked. Results across all Books are grouped in Book list order, a few per Book, so Pinned Books come first. The field never lets the keyboard learn what is typed.
- Deleting goes through `TrashRepository`: the Entry or Book is in the Trash at once, so "Urungkan" is a restore, and nothing waits for the snackbar to close. An Entry the editor empties is deleted for good, since it was never one to keep.
- Text styles (`entries/text_styles.dart`, rules in `spec/entry-format.md`): the text is stored with its marks as written, and only showing it reads them. One parser turns it into blocks (paragraphs, lists, quotes, monospace blocks) of runs, each remembering where it starts in the text as written, so search matches found in that text are laid over the styled text. The read view shows the blocks; Entry cards, the Book list's rows, and search snippets show the inline styles on one line. Monospace is the system's font. With the system's Bold text setting on, bold parts take a heavier weight than the rest. The editor (`entries/text_style_editing.dart`) keeps the text as written, marks and all, so the cursor moves over the marks: its controller styles the text with the same parser and dims the marks, the text selection menu adds or removes them, and Enter in a list item starts the next one.
- The editor saves as the user types (after a short pause, and when leaving or going to the background); an Entry with no text and no Images is discarded when the editor closes.
- Images: "Selipkan foto" takes photos from the Android photo picker (several at once, never more than the 20 an Entry holds) or the camera app, through `image_picker`, so the app asks for no storage or camera permission. Each photo is decoded by the platform's decoder (anything the device reads, HEIC included), turned upright by its EXIF orientation, and encoded again from its pixels alone, so no metadata survives (EXIF with GPS location, XMP, IPTC): the full image at most 2048 px on its longest side, JPEG quality 85, and the thumbnail at most 512 px, quality 80; neither is ever scaled up. Decoding runs on the engine's threads and encoding in a separate isolate. The file the picker or camera wrote is deleted once the photo is prepared. While it is prepared, the time the Image was taken is read from the original bytes in a separate isolate (`time_taken.dart`): EXIF `DateTimeOriginal`, found behind `Exif\0\0` wherever JPEG or HEIC keeps it, with `OffsetTimeOriginal`'s zone when there is one and as device local time otherwise; broken or partial times read as none. It comes back beside the stripped pixels in `ProcessedImage.timeTaken` and lives only in the editor's memory: it is never stored in the Entry, an Export, or sync, and closing the editor drops it. A new Entry whose Entry date is still the default offers the earliest time its Images were taken (skipping those after now) when that is more than an hour from the Entry date, in a popover under the date chip; only Pakai changes the Entry date, and Abaikan, a tap outside, typing, or the chip closes the offer for that Entry. A save sends new Images with their bytes and keeps existing ones by ID, so editing the text does not rewrite Image blobs. Cards and the editor show thumbnails; the read view and the viewer show the full image. Decrypted bytes never touch the disk: `EntryImageProvider` reads them from the repository and Flutter's in-memory image cache keeps the decoded images, so scrolling back does not open a blob again. An Image that does not open shows a broken-image placeholder.
- Covers (`books/cover_*.dart`, `books/book_cover.dart`): one photo from the photo picker or the camera app, through the same `PhotoPicker`, decoded upright at most 4096 px on its longest side to bound memory. The crop screen shows a fixed 3:4 frame over it; the user drags and pinches the photo, which always covers the frame. Selesai draws the framed part of the photo's pixels, at most 1536 px wide and never scaled up, into a new image (`processCover`), then encodes it like an Image: so the Cover is at most 1536×2048, JPEG quality 85, its thumbnail at most 384×512, quality 80, and no metadata survives. `BookRepository.setBookCover` stores it under a new Image ID each time. The Book list's rows and the Book screen's top bar show the thumbnail; Book info and the full-screen viewer show the full image. `BookCoverProvider` reads the bytes from the repository, like `EntryImageProvider`, keyed by the Cover's Image ID, so a replaced Cover is never shown from the image cache and decrypted bytes never touch the disk.
- Settings live in `shared_preferences` (`SharedPreferencesAsync`), not in the core's database: `theme_mode`, `language`, `has_started`, the Writing reminder's `writing_reminder`, `writing_reminder_time`, and `writing_reminder_skip`, `last_entry_created`, App lock's `app_lock`, `lock_again`, and `app_lock_suggested`, `last_export`, and the reminder to export's `export_reminder_later`. `main.dart` reads them before the first frame, so the app and the storage error screen start in the chosen theme and language; a missing or unknown value is the default. A change is saved in the background as it is picked. `has_started` is saved when Welcome creates the first Book, or when an Import adds a Book; an install without it that already has a Book counts as started and saves it, so deleting the last Book later shows the empty Book list, not Welcome. Like the store, settings are excluded from Android backup. They are device-only: never in an export, never synced.
- Local notifications: the Writing reminder (`reminder/`) is the app's only notification, scheduled on the device with no server and no plugin. Dart decides (`WritingReminderNotifier`): when it is on, the first reminder is today at the picked time if that is still ahead, else tomorrow; with "Lewati kalau sudah menulis", a day this device created an Entry on is skipped. That day comes from `last_entry_created`, saved when the editor creates an Entry, so the store is never read for it, in the background or otherwise, and deleting the Entry does not bring the reminder back. Dart schedules it again when the app opens or comes back (which picks up a time zone or device language change), when a setting or the app language changes, and when an Entry is created, through the `app.kronoer/reminder` method channel. Kotlin's `WritingReminder` keeps the time, the day to skip, and the text (in the app language at scheduling time) in its own preferences and sets one inexact `AlarmManager.setAndAllowWhileIdle` alarm, so it asks for no exact alarm permission and may come late, more so in Doze. `WritingReminderReceiver` posts the notification and sets the next alarm, never twice on one day, and sets it again after a restart, an app update, or a time or time zone change. The notification is fixed text ("Kronoer", "Apa yang terjadi hari ini?"), public on the lock screen, on one channel named "Writing reminder" in every language with no app icon badge; a tap opens the app on the Book tab, even when it was already open on another screen. `POST_NOTIFICATIONS` is asked when the switch is turned on (Android 13 and higher); denied, or notifications later turned off on the device, Settings says so and opens the app's notification settings.
- App lock (`lock/`) only decides whether the app is shown; it is never used for encryption, and the store opens the same either way (KRO-ADR-1). It asks for the device's own lock through `androidx.biometric`'s `BiometricPrompt` with `BIOMETRIC_WEAK | DEVICE_CREDENTIAL`, so any biometric or the device PIN, pattern, or password unlocks it, and Kronoer keeps no PIN of its own. The prompt needs a `FragmentActivity`, so `MainActivity` is a `FlutterFragmentActivity`; Kotlin's `AppLock` answers on the `app.kronoer/app_lock` method channel. `AppLockGate`, in `MaterialApp.router`'s builder, keeps the router built but offstage under the lock screen, so the open screen and any draft are there again after unlocking, and it answers the back button first while locked so nothing underneath is popped. `AppLockNotifier` locks on launch and when Kronoer has been in the background (from `onHide` to `onShow`, by the wall clock, a clock turned back counting as away) at least the Kunci lagi time: at once for Segera, else by a timer while away and a check on return. Trips Kronoer starts itself (`ownTrip` around the photo picker, the notification permission, and the prompt; `expectOwnTrip` before opening device settings) do not count. While App lock is on, Android 13 and higher keep the Recents preview blank with `setRecentsScreenshotEnabled(false)`; before that only `FLAG_SECURE` can, which also blocks screenshots, and Settings says so. With no screen lock on the device the switch cannot turn on; if the screen lock is removed while App lock is on, App lock turns itself off when Kronoer next shows and says so once. From the third Entry, across Books, the Book list suggests App lock in a card at the top while it is off and the device has a screen lock; Aktifkan goes through the same prompt as the switch, and once Nanti is tapped or App lock is turned on anywhere, `app_lock_suggested` keeps the card away. Only a real device's platform suggests it, so tests and the gallery never show the card.
- Locked Books open in the Book terkunci area, `Routes.lockedBooks` (`/locked`), whether App lock is on or not. Pulling the Book list down past its top shows its link while there is at least one Locked Book (`lockedBookSummariesProvider`); the link asks for the same prompt (`AppLockNotifier.openLockedBooks`) and opens `LockedBooksScreen`. A Book's screens are one route tree (`_bookRoute`) mounted twice, under `/books/:bookId` and `/locked/books/:bookId`, and screens keep linking by `Routes.book` and friends: the router's redirect sends a Locked Book's paths into the area while it is open, and anything in the area, or any Locked Book's path, to the Book list while it is closed. The area closes (`lockedBooksOpen` off) when the router moves from inside it to anywhere outside, and when Kronoer goes to the background, own trips excepted; Kunci lagi does not apply. Closing re-runs the redirect, which leaves the area. While it is open the Recents preview is hidden as for App lock (`hidesRecents`); one closed by going to the background keeps it hidden until Kronoer is back, as Recents shows the screen that went away. Outside the area nothing else shows a Locked Book: Pindahkan ke and the restore picker offer `destinationBooksProvider`, which adds the Locked Books only while the area is open, and the Trash list gathers items from Locked Books (`TrashItem.fromLockedBook`) into one "N item dari Book terkunci" card, which opens the area through the same prompt and shows them as usual until the Trash list is left or Kronoer goes to the background.
- Export (`export/`): the Export and Import pages share `ArchivePage`. Settings' Ekspor row is disabled ("Belum ada Entry") while no Entry is outside the Trash (`exportableEntryCountProvider`, from the Book and Locked Book lists' counts), and otherwise says when the last Export from this device finished (`last_export`, the time it started). It opens "Ekspor Data" (`settings/export`), which warns that the Archive will not be encrypted. Pilih lokasi first asks for the device's own lock when there is a Locked Book ("Ekspor semua Book"; without a screen lock it says to set one, and nothing is exported), then opens Android's picker for a new ZIP (`ACTION_CREATE_DOCUMENT`, `kronoer-YYYY-MM-DD.zip`) as an own trip. Kotlin's `ArchiveExport`, on the `app.kronoer/export` method channel, opens the picked file (`openFileDescriptor(uri, "wt")`) and hands Dart a copy of its descriptor (`dup().detachFd()`), which the core takes over and closes; Kotlin closes the original once the Archive is whole or deleted, which is what tells the provider the file is done (closing only the copy left Downloads showing 0 B) (`CoreStore.export_archive_to_fd`; Unix only, `export_archive_to_file` for tests). The core writes off the UI thread into an `ExportJob` whose atomic counters Dart polls every 100 ms for the progress page (`ExportNotifier`, `ArchiveWriter`); Batal sets its flag. While it writes, the screen stays on (`FLAG_KEEP_SCREEN_ON`) and back does nothing. A whole Archive is kept and Settings says "Arsip tersimpan" with its name as the storage shows it; a cancelled or failed one is deleted (`DocumentsContract.deleteDocument`, else emptied), and the failed page says whether the storage was full. From the pick until then the file's address is kept in Kotlin's own preferences with a persisted permission, so if Android stops Kronoer halfway, the next launch deletes it. Nothing about an Export reaches the server.
- The reminder to export (`export/export_reminder.dart`): the Book list shows one banner above the Books when there has been no Export for 30 days and Entries were created since, counting from the first Entry when there has been none (`exportReminderAt`). The core counts the Entries an Export would write, Locked Books included, by their plain `created_at` (`CoreStore.export_activity`). Ekspor opens the export page over the Book list (`/export`), which leaves back to it; Nanti hides the banner for 7 days. Only one banner shows at a time: while the reminder is due, the App lock card waits. An Import does not change `last_export`.
- Import (`import/`): Settings' Impor row opens "Impor dari arsip" (`settings/import`), and so does Welcome's "Punya arsip? Impor" (`welcome/import`), before any Book is made. An Import from Welcome that adds Books starts the app without "Buku Saya", and its summary stays open until Lihat hasilnya; closing the page, Batal, or a refused Archive goes back to Welcome. Pilih file opens Android's picker for a ZIP (`ACTION_OPEN_DOCUMENT`) as an own trip; no device lock is asked for, since the Archive is readable without Kronoer. Kotlin's `ArchiveImport`, on the `app.kronoer/import` method channel, opens the picked file for reading and hands Dart a copy of its descriptor, which the core takes over; a provider that only streams its file (no size) has it copied into the cache first, deleted at once and read through its open descriptor (`CoreStore.import_archive_from_fd`, `import_archive_from_file` for tests). The core imports off the UI thread into an `ImportJob` whose progress Dart polls every 100 ms (`ImportNotifier`, `ArchiveReader`): first "Memeriksa arsip", then "Arsip diperiksa" with what the Archive holds and "Menambahkan yang belum ada" with what is new and a bar of new Entries ready. The screen stays on, back does nothing, and Batal or Android stopping Kronoer leaves nothing: the store only changes in the last transaction. The summary page lists each Book it added to, then one row for all Locked Books without their names, then each Book in the Trash whose new Entries wait (restore it, then import again), then the rest; Lihat hasilnya opens the Book list. When the device had everything it says so instead. A refused Archive says whether it was damaged, newer, or had a photo that does not open, and nothing was added. Locked Books come in locked, on a device without a screen lock too; their link then asks for one. Import does not change `last_export`.
- Vector graphics (icons, brand, illustrations) are SVG sources in `app/vectors/`, compiled once by `tool/compile_vectors.dart` into the committed `.vec` files the app bundles from `app/assets/`. The Keyline Icons in `vectors/icons/stroke` and `fill` are replaced whole by `tool/keyline_icons.dart`; icons made for Kronoer, drawn the way Keyline draws its own, live in `vectors/icons/custom/` and compile into the same asset folders. Flutter's asset transformers are not used: they start one compiler process per SVG on every asset build, which exhausted memory.

## Server

- One Go module in `server/`; the binary is `cmd/kronoerserver` with `serve` and `migrate`. Migrations never run on startup.
- Packages under `internal/` are by feature (`serverinfo/`, later `account/`, `sync/`, `sharing/`); shared technical code lives in `internal/platform/`; generated code in `internal/gen/` is committed.
- API: Connect-RPC from `proto/` (packages `kronoer.<area>.v1`), served over HTTP/1.1 and unencrypted HTTP/2 behind a TLS proxy. Health uses the standard gRPC health service.
- Schema: goose migrations in `db/migrations/`, embedded in the binary.
- Object storage is reached through the S3 API only (AWS SDK for Go v2); any S3-compatible service works.
- Settings come only from `KRONOER_` environment variables. Logs never include blob contents.
- The server checks each Entry's readable header with its own Go parser, tested against `spec/test-vectors/`, and never touches the encrypted parts. `internal/entryheader` decodes a whole Entry or Image blob as strictly as the Rust core (deterministic CBOR, `format-version` first, a valid Entry date, nothing after the blob; the encrypted fields only for their sizes), then compares the header with what the upload claims: Entry ID, Book ID, and Book key version, or the Image ID. It fails with the spec's error codes. `serverinfo` reports the format versions it reads. Vectors whose fault is inside the encrypted parts (a failed tag, a payload listing an Image twice) pass its check, since only a holder of the keys can find them.
- Local development: PostgreSQL and RustFS from `server/compose.yaml`; recipes in `server/justfile`.

## Cryptography

The format is defined in `spec/entry-format.md`, with test vectors in `spec/test-vectors/`. Everything is encoded as deterministic CBOR and encrypted with XChaCha20-Poly1305.

- **Master key:** random, kept wrapped by an Android Keystore key (iOS Keychain later). Never derived from a password. It never encrypts anything itself: HKDF-SHA256 derives one subkey per purpose (`kronoer/v1/book-key-wrap`, `kronoer/v1/sqlcipher` for the local database, `kronoer/v1/star-record` and `kronoer/v1/star-id` for Star records, and `kronoer/v1/lock-record` and `kronoer/v1/lock-id` for Lock records).
- **Book key:** random and versioned; every Book has one, personal Books too. In a personal Book it is wrapped with the `book-key-wrap` subkey; in a shared Book it is also wrapped for each member with HPKE (V1).
- **Book record:** the Book's name, Description, and Cover reference (an Image reference to the Cover's two blobs, or none), sealed with the Book key. Its header (format version, Book ID, Book key version) stays readable and is bound to the encryption as associated data, like the wrapped Book key's.
- **Star record:** one Starred Entry (Entry ID, Book ID, starring time), sealed with the `star-record` subkey of the master key, never a Book key, so the other members of a shared Book never see it. Its readable header holds only a record ID, an HMAC-SHA256 of the Entry ID under the `star-id` subkey: the same star from two devices is one record, and whoever holds it cannot tell which Entry it is.
- **Lock record:** one Locked Book (Book ID, locking time), sealed and identified like a Star record, with the `lock-record` and `lock-id` subkeys and an HMAC of the Book ID. Locking and unlocking ask for the device's own lock through the same prompt as App lock (`setBooksLockedWithPrompt` in `lock/`), which never feeds into a key.
- **Entry key:** random and new on every save; encrypts the Entry's text, then is sealed with the Book key. The header (format version, Entry and Book IDs, Book key version, Entry date) stays readable and is bound to both encryptions as associated data.
- **Image key:** random per Image, kept while the Image stays attached. It seals two blobs, the full image and a thumbnail; the Entry's encrypted payload holds the key and the SHA-256 hash of each blob, so a swapped or changed blob is rejected before decryption.
- **Open keys stay in the core:** keys are wiped from memory when dropped, and Dart only handles encrypted blobs and plaintext content.
- **Entry signature (V1):** Ed25519 by the author over all entry fields, added with shared Books. Every edit is re-signed.
- **Key rotation:** a new Book key version is created when a member leaves or is removed.
- **Safety code:** fingerprint of a member's identity key. Comparing it is optional; the app warns when it changes.

## Accounts & devices (V1)

- Login: Google and passkey. Sign in with Apple arrives with iOS. No email/password.
- Moving or adding a device: Block Store restore, QR link from an existing device, or an optional printable recovery key. If all three are lost, synced data cannot be recovered.
- Push notifications for shared Books carry no content; the Book name is filled in on the device.

## Accepted security limits

- Entries already shared cannot be pulled back from a former member's device. The official app wipes its cache on removal; a modified app can keep it.
- The server sees metadata: who writes, when, and sizes.
- A member who never compares safety codes can be fooled by a malicious server inserting a fake key.
